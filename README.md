# A 股上市公司财务质量与选股分析系统

> 基于公开财经数据接口，构建 **数据采集 → 数仓分层 → SQL 分析 → 机器学习建模 → API 服务 → 可视化看板** 的完整数据链路。
> 从 5000+ 家 A 股上市公司的真实财报数据中，量化回答「哪些行业真正赚钱」「哪些公司财务质量高」「高股息率公司有什么共同特征」。

## 📌 这个项目解决什么问题

A 股有 5000 多家上市公司，财报数据公开但极其分散、口径不一。投资者和求职者想回答下面这些问题，通常只能靠零散的自媒体文章：

| 问题 | 本文档章节 | 用到的技术 |
|---|---|---|
| Q1 哪些行业盈利能力最强？行业间的 ROE 差距有多大？ | [行业质量分层](#) | SQL 聚合 + pandas 分组 |
| Q2 一家公司"财务质量高"能否被量化打分？ | [质量评分模型](#) | 特征工程 + 加权评分 |
| Q3 营收增长率能否用财务指标预测？ | [回归建模](#) | scikit-learn + 交叉验证 |
| Q4 高股息率公司有哪些共同的财务特征？ | [股息分析](#) | 分类模型 + 特征重要性 |

## 🤖 机器学习建模

**任务**：用财务指标预测上市公司 ROE（加权平均净资产收益率）

```bash
python scripts/08_train_model.py    # 训练与对比
python scripts/09_model_report.py   # 生成图表与分析报告
```

### 模型对比结果（5 折交叉验证）

| 模型 | 测试集 R² | 交叉验证 R² 均值 | 交叉验证标准差 | 判断 |
|---|---|---|---|---|
| **随机森林** | 0.6069 | **0.5412** | 0.0687 | ✅ 表现良好且稳定 |
| 梯度提升 | 0.6282 | 0.5355 | 0.0688 | ✅ 表现良好且稳定 |
| 基线（预测均值） | -0.0025 | -0.0010 | 0.0008 | 对照基准，预期为 0 |
| Ridge 回归 | 0.1944 | **-1.6078** | 3.5741 | ❌ 极不稳定，不可用 |

![模型对比](docs/figures/02_模型对比.png)

### 关键决策一：主动排除数据泄漏特征

用财务指标预测 ROE 时，最容易犯的错误是把 ROE 的组成部分当特征：

| 被排除的字段 | 原因 |
|---|---|
| `eps` | 每股收益，与 ROE 分子同源 |
| `bps` | 每股净资产，与 ROE 分母同源 |
| `net_profit` | 就是 ROE 的分子 |
| `net_margin` | = 净利润/营收，与 ROE 强相关 |
| `ocf_to_eps` | 分母含 eps，间接泄漏 |

放进去 R² 能轻松到 0.9 以上，但那不是预测，是**用另一种方式计算 ROE**。
代码中实现了**运行时防御**（`modeling.LEAKY_COLUMNS`），误加泄漏特征会直接抛异常。

### 关键决策二：用逐折诊断定位线性模型失效根因

Ridge 回归交叉验证 R² 为负、标准差超过 3。逐折诊断结果：

| 折 | 测试集 R² | 预测值范围 | 真实值范围 |
|---|---|---|---|
| 1 | 0.1944 | [-22, 59] | [-100, 60] |
| 2 | **-8.1113** | **[-1640, 58]** | [-100, 185] |
| 3 | 0.2027 | [-179, 65] | [-100, 63] |
| 4 | 0.1409 | [-16, 77] | [-100, 140] |
| 5 | 0.1707 | [-21, 74] | [-100, 200] |

- **不是过拟合**：单次划分下训练集 R²=0.1948、测试集 R²=0.1944，几乎相同 → **欠拟合**
- **是线性外推失控**：第 2 折预测出 `ROE = -1640%` 这种不可能的值，一个样本就把整折 R² 打成负数
- **树模型没有这个问题**：决策树的预测值只能是训练样本目标值的加权平均，**结构上不可能外推**

### 关键决策三：用排序能力论证模型价值

![预测vs真实](docs/figures/04_预测vs真实.png)

模型的价值不在于精确定价，而在于**排序筛选**。按预测值分 5 档：

| 预测档位 | 样本数 | 预测 ROE 均值 | **真实 ROE 中位数** |
|---|---|---|---|
| 最低 20% | 218 | -16.40 | **-10.14** |
| 较低 20% | 217 | 3.12 | 2.15 |
| 中间 20% | 217 | 6.12 | 5.66 |
| 较高 20% | 217 | 8.78 | 8.61 |
| 最高 20% | 217 | 13.56 | **11.67** |

**严格单调递增**，最低档与最高档相差 **21.8 个百分点** —— 足以支撑初筛场景。

## 📊 工程要点（面试可讲的亮点）

### 1. 分层架构，而不是一个大脚本

`config` 管配置、`http` 管网络、`cache` 管缓存、`storage` 管落地、`sources` 管数据源。
新增一个数据源只需在 `sources/` 下加一个文件，**不改动任何已有代码**。

### 2. 取数与解析分离

网络请求是稀缺资源（会被限流），解析逻辑却经常要改。
两者分离后，修改解析逻辑可以直接用本地缓存重跑，**不需要重新请求接口**。

### 3. 指数退避重试 + 请求限速

```python
wait = 2 ** (attempt - 1)   # 1s → 2s → 4s，给对方服务器恢复时间
```

失败重试不是"立刻重试"，而是逐渐拉长间隔——这比固定间隔成功率更高。

### 4. 原始数据落盘 + 原子写

```python
tmp.write_text(...)   # 先写临时文件
tmp.replace(path)     # 再原子替换，避免中断产生半截文件
```

### 5. 故障隔离

单个报告期采集失败**不会中断**其他报告期的采集（`scripts/02_collect_finance.py`）。
一条流水线不应该因为一个数据源挂掉就整体崩溃。

### 6. 幂等性

`if_exists="replace"` + `drop_duplicates()` 保证**重复运行结果一致**，
这是数据管道的基本要求。

### 7. 数据质量标记而非直接删除

对异常值（净利润为负、ROE 极端值、关键字段缺失）打标记列而不是删除，
因为"哪些公司异常"本身就是分析素材，删除还会导致公司总数与财报披露数对不上。

## 🐛 踩坑记录（面试素材）

开发过程中遇到两个值得记录的坑，完整过程见 [`docs/notes/02-排查记录-接口限流.md`](docs/notes/02-排查记录-接口限流.md)：

### 坑 1：接口 IP 限流，以及我的三次误判

行情接口在请求量累积后对本机 IP 限流，表现为 `RemoteDisconnected`（TCP 能连、TLS 能握手，但服务端收到请求直接断开）。

**我连续三次误判根因**：改 Referer → 成功 → 以为修好；改连接头 → 成功 → 以为修好；换 HTTP 库 → 成功 → 以为修好。实际上该接口本身会间歇性放行，单次成功不能作为证据。

**正确的验证方法**：同一时刻 + 对照组 + 足量样本（10 次连续请求）。用这个方法才最终确认：换任何 HTTP 库、任何请求头、任何参数都失败 → 问题在服务端而非客户端。

**工程应对**（而不是绕限制）：原始数据落盘做缓存、主数据源降级到未被限流的接口、新增数据源健康巡检。

### 坑 2：数据库写入静默失败

日志报告"已写入 23,246 行"、CSV 也确实有 23,246 行，但 `SELECT COUNT(*)` 返回 **0**。诊断依据 `PRAGMA freelist_count = 772`，说明"建表 → 插入 → 事务回滚"。

根因：pandas 的 `to_sql` 与 sqlite3 隐式事务边界不一致（DDL 生效而 DML 被回滚）。

修复：改用显式 `CREATE TABLE + executemany + commit`，并**在写入后立即回读校验行数**，不一致直接抛异常。**静默的数据丢失比直接报错危险得多。**
