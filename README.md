# A 股上市公司财务质量与选股分析系统

基于公开财经数据接口，构建 **数据采集 → 数仓分层 → SQL 分析 → 机器学习建模 → API 服务 → 可视化看板** 的完整数据链路。

从 5,659 家 A 股上市公司的真实财报数据中，量化回答「哪些行业真正赚钱」「规模是否带来盈利优势」「高股息公司有什么共同特征」。

## 📌 项目解决的问题

A 股有 5,000 多家上市公司，财报数据公开但极其分散、口径不一。本文档回答四个问题：

| 问题 | 使用技术 | 相关文件 |
|---|---|---|
| Q1 哪些行业盈利质量最高？行业间差距有多大？ | SQL 聚合、分位数统计 | `sql/01_industry_ranking.sql` |
| Q2 公司规模与盈利能力是什么关系？ | 分箱对比、假设检验 | `sql/03_scale_effect.sql` |
| Q3 高股息率公司是否财务质量更好？ | 分组对比、相关性分析 | `sql/05_dividend_quality.sql` |
| Q4 盈利能力能否用财务指标预测？ | scikit-learn 回归 + 交叉验证 | `src/jmintel/modeling.py` |

### ⚠️ 合规说明

本项目**只使用公开、无需登录的数据接口**，并且：

- ❌ 不抓取任何需要登录的网站
- ❌ 不绕过任何验证码、风控或反爬机制
- ❌ 不采集、不存储任何个人信息
- ✅ 已实现请求限速（默认 1 秒/次）与指数退避重试，避免对数据提供方造成压力
- ✅ 原始数据落盘缓存，重复运行不重复请求

> 开发过程中行情接口曾对请求源做 IP 限流。**应对方式是改用公开的财务接口 + 完善缓存层，
> 而不是设法绕过限制。** 完整排查过程见 [`docs/notes/02-排查记录-接口限流.md`](docs/notes/02-排查记录-接口限流.md)。

## 🚀 快速开始

### 1. 环境要求

- Python 3.12+
- 无需数据库服务（使用 SQLite 文件库）

### 2. 安装

```bash
git clone https://github.com/75killer/job-market-intel.git
cd job-market-intel

python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
# 需要完全复现环境时用锁定版本：
# pip install -r requirements.lock.txt
```

### 3. 完整流程（按顺序执行）

```bash
# ① 数据源健康巡检（确认源可用再动手）
python scripts/00_health_check.py

# ② 采集财报数据（首次约 1 分钟，之后走本地缓存秒级完成）
python scripts/02_collect_finance.py --report-date 2024-12-31 --report-date 2025-06-30

# ③ 数据质量体检（确认分析口径）
python scripts/03_data_quality_check.py

# ④ 构建数仓分层：ods -> dwd -> ads
python scripts/05_build_dwd_ads.py

# ⑤ 执行 10 个业务分析 SQL，结果归档到 docs/analysis/
python scripts/07_run_sql.py --report-date 2024-12-31

# ⑥ 训练模型（对比 4 种算法）
python scripts/08_train_model.py

# ⑦ 生成模型图表与分析报告
python scripts/09_model_report.py
```

### 4. 启动服务与看板

```bash
# FastAPI 模型服务（交互式文档 http://127.0.0.1:8000/docs）
uvicorn api.main:app --reload --port 8000

# Streamlit 交互看板（http://127.0.0.1:8501）
streamlit run dashboard/app.py
```

### 5. 直接用 SQL 查询

```bash
sqlite3 data/jmintel.db "SELECT industry, COUNT(*) AS 公司数, ROUND(AVG(roe),2) AS 平均ROE \
FROM dwd_finance_performance WHERE is_analyzable=1 AND report_date='2024-12-31' \
GROUP BY industry ORDER BY 平均ROE DESC LIMIT 10;"
```

## 📊 数据规模

| 指标 | 数值 |
|---|---|
| 原始记录 | **23,246 行 × 27 列** |
| 报告期 | 2 个（2024 年报、2025 半年报） |
| 覆盖公司（原始） | 11,640 家 |
| **有效分析口径** | **5,659 家 A 股上市公司 / 128 个行业** |
| 全市场 ROE 中位数 | 2024 年报 4.69% / 2025 半年报 2.52% |

### 数据口径说明（分析结论的前提）

| 处理 | 原因 |
|---|---|
| **锁定单一报告期** | ROE = 净利润 / 净资产。半年报只累计半年利润，分母却是期末净资产，因此半年报 ROE 天然约为年报的一半（实测：年报 4.69% vs 半年报 2.52%）。**跨报告期比较 ROE 无意义。** |
| **剔除新三板 / 老三板** | 原始数据中新三板占 **47.5%**（5,756 家）且行业分类 **100% 缺失**。它们是"挂牌"不是"上市"，混入会导致行业结论完全错误。 |
| **剔除已退市公司** | 名称含"摘牌/退市"的记录（34 条），已无分析意义。 |
| **保留但单独标记 ST** | ST/*ST 是退市风险警示股（约 211 家），属于 A 股的一部分，删除会让亏损统计失真，因此标记 `is_st` 而非删除。 |
| **使用中位数而非平均值** | 行业里只要有一家公司 ROE 是 2000%，平均值就被彻底带偏，中位数对极端值免疫。 |
| **设置最少公司数门槛** | 只有 2–3 家公司的行业，"行业中位数"没有统计意义，聚合表用 `is_reliable` 字段标记。 |

## 🤖 机器学习建模

**任务**：用财务指标预测上市公司 ROE

```bash
python scripts/08_train_model.py    # 训练与对比
python scripts/09_model_report.py   # 生成图表与分析报告
```

### 模型对比结果（5 折交叉验证）

| 模型 | 测试集 R² | 交叉验证 R² 均值 | 交叉验证标准差 | 判断 |
|---|---|---|---|---|
| **随机森林** | 0.6069 | **0.5412** | 0.0687 | ✅ 表现良好且稳定 |
| 梯度提升 | 0.6282 | 0.5355 | 0.0688 | ✅ 表现良好且稳定 |
| 基线（预测均值） | -0.0025 | -0.0010 | 0.0008 | 对照基准，预期为 0 |
| Ridge 回归 | 0.1944 | **-1.6078** | 3.5741 | ❌ 极不稳定，不可用 |

![模型对比](docs/figures/02_模型对比.png)

### 设计决策一：主动排除数据泄漏特征

用财务指标预测 ROE 时，最容易犯的错误是把 ROE 的组成部分当特征：

| 被排除的字段 | 原因 |
|---|---|
| `eps` | 每股收益，与 ROE 分子同源 |
| `bps` | 每股净资产，与 ROE 分母同源 |
| `net_profit` | 就是 ROE 的分子 |
| `net_margin` | = 净利润/营收，与 ROE 强相关 |
| `ocf_to_eps` | 分母含 eps，间接泄漏 |
| `roe` / `roe_tier` | 目标变量本身及其派生 |

纳入这些字段可以让 R² 轻松超过 0.9，但那不是预测，而是**用另一种方式计算 ROE**。
代码中实现了运行时防御（`modeling.LEAKY_COLUMNS`），误加泄漏特征会直接抛异常。

### 设计决策二：用逐折诊断定位线性模型失效根因

Ridge 回归交叉验证 R² 为负、标准差超过 3。逐折诊断结果：

| 折 | 测试集 R² | 预测值范围 | 真实值范围 |
|---|---|---|---|
| 1 | 0.1944 | [-22, 59] | [-100, 60] |
| 2 | **-8.1113** | **[-1640, 58]** | [-100, 185] |
| 3 | 0.2027 | [-179, 65] | [-100, 63] |
| 4 | 0.1409 | [-16, 77] | [-100, 140] |
| 5 | 0.1707 | [-21, 74] | [-100, 200] |

- **不是过拟合**：单次划分下训练集 R²=0.1948、测试集 R²=0.1944，几乎相同 → **欠拟合**
- **是线性外推失控**：第 2 折预测出 `ROE = -1640%`，一个样本就把整折 R² 打成负数
- **树模型没有这个问题**：决策树的预测值只能是训练样本目标值的加权平均，结构上不可能外推

### 设计决策三：用排序能力论证模型价值

![预测vs真实](docs/figures/04_预测vs真实.png)

模型的价值不在于精确定价，而在于**排序筛选**。按预测值分 5 档：

| 预测档位 | 样本数 | 预测 ROE 均值 | **真实 ROE 中位数** |
|---|---|---|---|
| 最低 20% | 218 | -16.40 | **-10.14** |
| 较低 20% | 217 | 3.12 | 2.15 |
| 中间 20% | 217 | 6.12 | 5.66 |
| 较高 20% | 217 | 8.78 | 8.61 |
| 最高 20% | 217 | 13.56 | **11.67** |

**严格单调递增**，最低档与最高档相差 **21.8 个百分点**。

![特征重要性](docs/figures/03_特征重要性.png)

### 已实验验证无效的方向：行业特征

曾假设"行业是 ROE 最强的解释变量"，实测**不成立**：

| 特征集 | 随机森林 R² | 梯度提升 R² |
|---|---|---|
| 财务特征（7 个） | 0.5601 | 0.5681 |
| 财务特征 + 行业哑变量 | 0.5586 (-0.0015) | 0.5666 (-0.0015) |
| 仅 128 个行业哑变量 | 0.0198 | 0.0260 |

**方差分解揭示了根因**：行业间差异只占 ROE 总方差的 **7.8%**，
剩余 **92.2%** 来自行业内公司差异（行业内标准差 13.86 vs 行业间 6.77）。

原推理错在把「行业均值差异大」当成了「行业能解释个体差异」。
完整实验见 [`docs/notes/07-实验记录-行业特征负结果.md`](docs/notes/07-实验记录-行业特征负结果.md)，
可复现脚本 `scripts/10_industry_feature_experiment.py`。

## 🔍 SQL 业务分析（10 个场景）

所有分析语句在 [`sql/`](sql/) 目录下，一条命令批量执行并归档结果：

```bash
python scripts/07_run_sql.py --report-date 2024-12-31
# 结果输出到 docs/analysis/（Markdown 报告 + CSV）
```

| # | 文件 | 业务问题 | SQL 技术点 |
|---|---|---|---|
| 01 | `01_industry_ranking.sql` | 哪些行业盈利质量最高？ | 窗口函数 `RANK()`、分位数、条件聚合 |
| 02 | `02_quality_distribution.sql` | 全市场质量分布如何？ | `CASE WHEN` 分箱、占比计算 |
| 03 | `03_scale_effect.sql` | 规模越大越赚钱吗？ | 区间分箱 + 假设检验 |
| 04 | `04_top_bottom_companies.sql` | 各行业最赚钱的公司是谁？ | `ROW_NUMBER() OVER (PARTITION BY ...)` |
| 05 | `05_dividend_quality.sql` | 高股息公司质量更好吗？ | 分组对比验证假设 |
| 06 | `06_peer_comparison.sql` | 单公司在同行中的水平？ | CTE 预聚合 + JOIN |
| 07 | `07_market_board_analysis.sql` | 各上市板块质量差异？ | 条件聚合、多维度交叉 |
| 08 | `08_growth_analysis.sql` | 哪些行业在增长？ | 二维分象限（成长性 × 盈利能力） |
| 09 | `09_cashflow_quality.sql` | 利润是真金白银吗？ | 比率分析、`NULLIF` 防除零 |
| 10 | `10_risk_watchlist.sql` | 哪些公司有财务风险？ | 多信号加权评分筛选 |

**技术细节**：SQLite 没有内置 `MEDIAN` / `STDDEV`，项目通过 `create_aggregate` 注册了
自定义聚合函数（见 `scripts/07_run_sql.py`），因此 SQL 里始终写标准写法 `MEDIAN(x)`，
换到 PostgreSQL / DuckDB 也能直接运行。

**已知限制**：SQLite 不支持把自定义聚合函数用作窗口函数
（`MEDIAN(x) OVER (PARTITION BY ...)` 会报错），
因此组内比较类查询改用「CTE 预聚合 + JOIN」的标准写法实现。

## 📈 分析结论

> 报告期：2024 年报 | 口径：5,659 家真实 A 股（已剔除新三板/退市/ST）

### 结论 1：行业盈利质量分层明显

| 排名 | 行业 | 公司数 | ROE 中位数 | 净利率中位数 | 毛利率中位数 | 亏损占比 |
|---|---|---|---|---|---|---|
| 1 | 白酒Ⅱ | 20 | **18.33%** | 23.26% | 73.55% | 5.00% |
| 2 | 贵金属 | 13 | 11.96% | 5.17% | 25.84% | 7.69% |
| 3 | 调味发酵品Ⅱ | 14 | 11.34% | 12.50% | 35.85% | 0.00% |
| 4 | 白色家电 | 11 | 11.18% | 5.53% | 20.78% | 9.09% |
| 5 | 小家电 | 24 | 10.93% | 6.74% | 28.51% | 4.17% |

ROE 中位数最低：影视院线（-0.87%）、软件开发（-0.18%，133 家公司亏损占比过半）、
军工电子Ⅱ（0.02%）、房地产开发（0.04%）、普钢（0.07%）。

**解读**：软件开发行业 133 家公司 ROE 中位数为负、亏损占比超过一半，
与"软件行业高薪"的直觉相反 —— **行业薪酬水平与行业平均盈利能力不是一回事**。

### 结论 2：规模效应存在，但毛利率反向变化

| 规模档 | 公司数 | 占比 | ROE 中位数 | 净利率中位数 | 毛利率中位数 | 亏损占比 |
|---|---|---|---|---|---|---|
| 微型（<10亿） | 1,798 | 33.13% | 3.25% | 6.53% | **31.74%** | 31.09% |
| 小型（10-50亿） | 2,211 | 40.74% | 5.11% | 5.30% | 23.68% | 21.39% |
| 中型（50-200亿） | 910 | 16.77% | 6.67% | 5.04% | 20.82% | 12.97% |
| 大型（200-1000亿） | 387 | 7.13% | 8.16% | 3.85% | 14.84% | 12.40% |
| 超大型（>1000亿） | 121 | 2.23% | **9.69%** | 3.31% | **11.59%** | 7.44% |

**两个方向相反的发现**：
1. **ROE 与规模正相关**：3.25% → 9.69%，亏损占比 31.09% → 7.44%
2. **毛利率与规模负相关**：31.74% → 11.59%

大规模公司多集中在制造业、能源、金融等**低毛利高周转**行业。
**不能只看毛利率判断公司质量，ROE 才是综合指标。**

### 结论 3：高股息率公司的财务质量显著更好

| 股息档 | 公司数 | ROE 中位数 | 净利率中位数 | 成长性中位数 | 亏损占比 | 优秀公司占比 |
|---|---|---|---|---|---|---|
| 0-不分红 | 1,754 | **-3.43%** | -4.16% | -10.92% | **62.09%** | 10.49% |
| 1-低（<1%） | 1,882 | 4.67% | 6.10% | 2.34% | 4.14% | 6.54% |
| 2-中（1%-3%） | 1,403 | 8.52% | 9.52% | 5.26% | 2.28% | 15.04% |
| 3-高（3%-5%） | 316 | 10.66% | 10.30% | 0.38% | 1.58% | 22.15% |
| 4-很高（>5%） | 72 | **11.09%** | 8.77% | **-1.81%** | 4.17% | **30.56%** |

**结论**：「高股息 = 高质量」基本成立 —— 高股息组 ROE 中位数是不分红组的 3 倍多。

**但有一个关键例外**：股息率 >5% 组的**成长性中位数为 -1.81%**（唯一为负的组），
说明超高股息往往伴随增长停滞 —— 公司没有更好的再投资机会，只能把钱分掉。

### 结论 4：过半公司利润含金量高，但 12% 现金流为负

| 现金流档 | 公司数 | 占比 | 现金利润比中位数 | ROE 中位数 | 净利率中位数 |
|---|---|---|---|---|---|
| 1-含金量高 | 2,376 | 56.26% | 2.257 | 5.83% | 6.63% |
| 2-含金量中 | 672 | 15.91% | 1.006 | 10.61% | 13.39% |
| 3-含金量低 | 649 | 15.37% | 0.532 | 9.28% | 11.00% |
| 4-现金流为负 | 521 | 12.34% | -1.480 | 4.28% | 4.51% |

（现金利润比 = 每股经营现金流 / 每股收益）

**结论**：有 **12.34%（521 家）公司账面盈利、经营现金流却为负** ——
这类公司利润可能大量停留在应收账款上，是财务质量的重点关注对象。

### 结论 5：全市场质量分布 —— 优秀公司仅占一成

| 质量档 | 公司数 | 占比 | 档内 ROE 中位数 |
|---|---|---|---|
| 优秀（ROE ≥ 15%） | 610 | 11.24% | 19.70% |
| 良好（8% ≤ ROE < 15%） | 1,247 | 22.98% | 10.57% |
| 一般（0 ≤ ROE < 8%） | 2,363 | 43.54% | 4.01% |
| 亏损（ROE < 0） | 1,207 | 22.24% | -9.03% |

## ⚙️ 工程实现要点

### 1. 分层架构，而非单体脚本

`config` 管配置、`http` 管网络、`cache` 管缓存、`storage` 管落地、
`features` 管特征、`modeling` 管建模、`sources` 管数据源。
新增数据源只需在 `sources/` 下加一个文件，**不改动任何已有代码**。

### 2. 取数与解析分离

网络请求是稀缺资源（会被限流），解析逻辑却经常要改。
两者分离后，修改解析逻辑可以直接用本地缓存重跑，**不需要重新请求接口**。

### 3. 指数退避重试 + 请求限速

```python
wait = 2 ** (attempt - 1)   # 1s → 2s → 4s，给对方服务器恢复时间
```

### 4. 原始数据落盘 + 原子写

```python
tmp.write_text(...)   # 先写临时文件
tmp.replace(path)     # 再原子替换，避免中断产生半截文件
```

### 5. 故障隔离

单个报告期采集失败**不会中断**其他报告期的采集。
一条流水线不应该因为一个数据源挂掉就整体崩溃。

### 6. 幂等性

`drop_duplicates()` + 按主键 upsert 保证**重复运行结果一致**。
实测连续运行两次，数据库行数均为 23,246，无重复数据。

### 7. 写入后强制回读校验

```python
actual = conn.execute(f'SELECT COUNT(*) FROM "{name}"').fetchone()[0]
if actual != len(df):
    raise RuntimeError(f"写库校验失败：期望 {len(df)} 行，实际 {actual} 行")
```

### 8. 数据质量标记而非直接删除

对异常值（净利润为负、ROE 极端值、关键字段缺失）打标记列而不是删除，
因为"哪些公司异常"本身就是分析素材，删除还会导致公司总数与披露数对不上。

## 🐛 开发过程记录

### 问题 1：数据源 IP 限流，以及连续三次误判

行情接口在请求量累积后对请求源限流，表现为 `RemoteDisconnected`
（TCP 能连、TLS 能握手，但服务端收到请求直接断开）。

排查过程中我**连续三次误判根因**：改请求头 → 单次成功 → 认为修好；
改连接参数 → 单次成功 → 认为修好；换 HTTP 库 → 单次成功 → 认为修好。
实际上该接口本身会间歇性放行，**单次成功不能作为证据**。

最终用「同一时刻 + 对照组 + 连续 10 次请求」的方式确认：
换任何 HTTP 库、任何请求头、任何参数都失败 → 问题在服务端而非客户端。

**工程应对**（而非绕过限制）：原始数据落盘做缓存、主数据源降级到未被限流的接口、
新增数据源健康巡检脚本。

### 问题 2：数据库写入静默失败

日志报告"已写入 23,246 行"、CSV 也确实有 23,246 行，但 `SELECT COUNT(*)` 返回 **0**。

诊断依据 `PRAGMA freelist_count = 772`，说明"建表 → 插入 → 事务回滚"。
根因是 pandas 的 `to_sql` 与 sqlite3 隐式事务边界不一致（DDL 生效而 DML 被回滚）。

修复：改用显式 `CREATE TABLE + executemany + commit`，并**在写入后立即回读校验行数**。

### 问题 3：SQLite 布尔类型导致的行筛选失效

SQLite 没有原生 BOOLEAN 类型，布尔值存成 0/1 整数。
读回后 `df[df["is_analyzable"]]` 在 pandas 3.0 下被解释为"选取名为 1/0 的列"，
抛出 `KeyError`。

修复：在 `storage.BOOLEAN_COLUMNS` 中集中声明布尔列，写入时转 0/1、读出时还原 bool。

### 问题 4：数值格式化的静默错误

`%` 风格格式化不支持千位分隔符，`"%14,.0f" % value` 会把格式串原样打印出来。
改用 f-string（`f"{value:>14,.0f}"`）。
**这类问题不报错、只是输出错，所以必须人工检查日志。**
