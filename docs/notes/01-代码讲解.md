## 一、整体结构：为什么要分这么多文件夹？

```
job-market-intel/
├── src/jmintel/          ← 核心逻辑（可以被复用、被测试）
│   ├── config.py         全局配置：路径、常量、参数
│   ├── logging_setup.py  日志：让程序会说话
│   ├── http.py           网络请求：统一超时/重试/限速
│   ├── storage.py        存储：落盘 + 写数据库
│   └── sources/          数据源适配器（一个源一个文件）
├── scripts/              ← 入口脚本（命令行能直接跑的）
├── data/                 ← 数据（不入 git）
│   ├── raw/              原始数据，只增不改
│   ├── interim/          中间数据
│   └── processed/        最终干净数据
├── sql/                  ← 分析用的 SQL 语句
├── notebooks/            ← 探索性分析（Jupyter）
├── tests/                ← 单元测试
├── models/               ← 训练好的模型文件
└── docs/                 ← 文档、图片、笔记
```

**设计说明**：
> "我把项目分成逻辑层和入口层：`src/` 放可复用的逻辑，`scripts/` 只放入口。
> 这样同一个采集逻辑既能被命令行调用，也能被测试和定时任务调用，不会重复写。"

## 二、`config.py` —— 告别到处写死路径

**它解决什么问题？**
新手最常见的写法是在每个文件里写 `open("D:\\我的项目\\data.csv")`。
换台电脑、换个人跑，立刻报 `FileNotFoundError`。

**核心代码**：

```python
PROJECT_ROOT = Path(__file__).resolve().parents[2]
```

拆开看：
- `__file__` → 当前文件（config.py）的路径
- `.resolve()` → 转成绝对路径，去掉 `..` 这类相对符号
- `.parents[2]` → 往上数两级：`config.py` 的父目录是 `jmintel/`，
  再往上是 `src/`，再往上是项目根目录

所以无论项目放在哪个盘、哪台机器，`PROJECT_ROOT` 永远正确，这就是路径配置的**可移植性**。

```python
DB_PATH: Path = DATA_DIR / "jmintel.db"
```
`Path` 对象用 `/` 拼接路径（Windows 上也会自动处理成 `\`），
比字符串拼接 `"a" + "\\" + "b"` 安全得多。

**自检问题**（能答出来才算懂）：
1. 为什么要有个 `ensure_dirs()`？不写会怎样？
   <details><summary>答案</summary>
   不写的话，第一次运行时 `data/raw/` 不存在，写文件会抛 `FileNotFoundError`。
   `mkdir(parents=True, exist_ok=True)` 的意思是：父目录一起建，已存在也不报错。
   </details>
2. `get_env()` 是干嘛的？
   <details><summary>答案</summary>
   从环境变量读敏感信息（如 API token）。绝不把密码写进代码再传 GitHub——
   这是真实事故的高发点。
   </details>

## 三、`logging_setup.py` —— 让程序会说话

**它解决什么问题？**
新手用 `print()` 调试，有两个致命缺点：
1. 分不清是正常信息还是错误
2. 程序跑完之后什么都没留下，出问题无法回溯

**四个日志级别，什么时候用哪个**：

| 级别 | 什么时候用 | 例子 |
|---|---|---|
| `DEBUG` | 调试细节，平时不显示 | "当前页参数是 {...}" |
| `INFO` | 正常进度，要让人看到 | "第 3 页完成，累计 300 条" |
| `WARNING` | 有问题但能继续 | "字段 f23 缺失，已跳过" |
| `ERROR` | 出错了，任务可能要中止 | "请求最终失败：..." |

**核心代码**：

```python
logger = logging.getLogger(__name__)
```
`__name__` 会自动变成模块名，比如 `jmintel.sources.eastmoney`。
所以日志里能看出是哪一层打的 —— 定位问题时极其有用。

**自检问题**：
1. 为什么用 `logging` 而不是 `print`？
2. 日志里为什么要带时间戳？（提示：想想"这个 bug 是什么时候开始的"）

## 四、`http.py` —— 最容易被忽略、但最重要的一层

**它解决什么问题？**
如果每个爬虫都直接 `requests.get(url)`，会出三个问题：

| 问题 | 后果 |
|---|---|
| 没设超时 | 对方不响应时程序永久卡死 |
| 没重试 | 一次网络抖动，整个任务白跑 |
| 没限速 | 请求太猛被封 IP，任务彻底失败 |

**关键设计 1：指数退避重试**

```python
wait = 2 ** (attempt - 1)   # 第1次失败等1s，第2次等2s，第3次等4s
```

为什么不固定等 1 秒？
因为对方服务器可能是**临时过载**。立刻重试只会加重它的负担；
逐渐拉长间隔，给对方恢复的时间，成功率更高。
（这是处理外部依赖故障的通用做法）

**关键设计 2：限速**

```python
elapsed = time.monotonic() - self._last_request_at
if elapsed < self.interval:
    time.sleep(self.interval - elapsed)
```

用 `time.monotonic()` 而不是 `time.time()`：
后者会受系统时间调整影响（比如自动校时），前者只单调递增，算间隔更可靠。

**关键设计 3：Session 复用连接**

```python
self.session = requests.Session()
```
每次新建连接都要 TCP 握手 + TLS 握手，很慢。
`Session` 会复用连接池，还自动保持 Cookie。

**关键设计 4：`raise_for_status()`**

```python
resp.raise_for_status()
```
HTTP 状态码 4xx/5xx 时抛异常。
**为什么重要**：如果不写，服务器返回 403 错误页时，
你的代码会"成功"解析出一堆垃圾数据，还不报错——这是最坑的 bug。

**自检问题**：
1. 重试三次都失败了会怎样？（答案：抛 `RuntimeError`，把原始异常用 `from` 串起来）
2. 为什么要用 `with HttpClient() as client`？
   （答案：保证 `close()` 一定被调用，释放连接。这叫上下文管理器）

## 五、`sources/eastmoney.py` —— 适配器模式

**它解决什么问题？**
不同数据源的接口格式完全不同。如果把它们混在一起写，
以后加一个新数据源就会把代码搞成一团乱麻。

**做法**：每个数据源一个文件，统一暴露两个函数：
- `fetch_xxx()` → 负责取数（网络）
- `parse_xxx()` → 负责解析（把 JSON 变成 DataFrame）

**为什么要把「取数」和「解析」分开？**
> "因为网络请求是稀缺资源——请求一次要花时间、可能被封。
> 解析逻辑却经常要改（字段改名、加派生字段、修 bug）。
> 分开之后，改解析逻辑时可以直接用本地已保存的原始 JSON 重跑，
> 不需要重新请求对方服务器。这也让解析逻辑可以写单元测试。"

**字段映射的设计**：

```python
QUOTE_FIELD_MAP = {"f12": "stock_code", "f14": "stock_name", ...}
```

接口返回的是 `f12`、`f20` 这种天书字段。直接当列名的话，
三个月后自己都看不懂，更别说让其他人维护。
用映射表改名，好处是**要改字段只改这一张表**。

**数据类型转换的坑**：

```python
df[col] = pd.to_numeric(df[col], errors="coerce")
```

`errors="coerce"` 的意思是"转不了的变成 NaN，不要报错"。
为什么需要？因为接口用 `"-"` 表示缺失值。
如果不转换，这一列会是 `object`（字符串）类型，
后面算平均值会得到奇怪的结果甚至报错。

> **延伸问题**：pandas 里 `NaN` 和 `None` 有什么区别？为什么数值列混入字符串会导致后续计算出错？

**自检问题**：
1. `max_pages` 参数是干嘛的？为什么调试时要先跑 1 页？
   （答案：先小规模验证，确认字段和逻辑没问题，再全量跑。
   避免吭哧跑 10 分钟才发现字段名写错了）
2. `market_cap_yi` 这个字段是哪来的？
   （答案：代码里自己算的，把"元"换算成"亿元"，为了可读性）

## 六、`storage.py` —— 数据分层落地

**核心概念：为什么要保存原始数据？**

```
接口返回 JSON  ──保存──>  data/raw/xxx_20261010_183359.json   ← 原样存，永不覆盖
                        │
                        └──解析──> data/processed/ods_company_spot.csv  ← 规范表
```

如果只存解析后的结果，那么解析代码写错时，你只能**重新请求**对方服务器。
存了原始数据，就能反复重跑解析逻辑，既快又不会给对方压力。
带时间戳命名则保证每次采集都留档，可以对比"今天的数据 vs 上周的数据"。

**三个实用细节**：

1. `if_exists="replace"` —— 每次重建表，保证**幂等**
   （重复运行结果一致，这是数据管道的基本要求）
2. `encoding="utf-8-sig"` —— 让 Excel 打开中文不乱码
   （多出来的 BOM 头就是给 Excel 认的）
3. 空 DataFrame 直接跳过并警告，不要写出一个 0 字节的坏文件

**自检问题**：
1. 什么是"幂等"？为什么数据管道要求幂等？
2. `data/raw/` 为什么写进 `.gitignore`？
   （答案：数据能重新采集得到，传上去会让仓库巨大且变慢）

## 七、`scripts/01_collect_company_spot.py` —— 入口脚本

**为什么开头有这几行？**

```python
PROJECT_ROOT = Path(__file__).resolve().parents[1]
sys.path.insert(0, str(PROJECT_ROOT / "src"))
```

Python 默认只从"已安装的包"和"当前目录"找模块。
我们的代码在 `src/` 下、又没安装成包，所以手动把 `src/` 加进搜索路径。
（另一种做法是 `pip install -e .`，那是更正式的方案，以后可以升级）

**流程是清晰的五步**：
```
1. 请求原始数据     → records
2. 原始数据落盘     → data/raw/*.json
3. 解析成规范表     → DataFrame
4. 写 CSV + 数据库  → data/processed/*.csv + jmintel.db
5. 打印预览 + 统计  → 让人肉眼确认结果合理
```

**为什么要有第 5 步？**
因为"程序不报错"不等于"数据是对的"。
可能接口改了字段，你抓回来一堆空值却毫无察觉。
**打印几行样例 + 统计量，是最便宜的质检手段。**

**自检问题**：
1. `argparse` 是干嘛的？为什么不用硬编码？
2. `if __name__ == "__main__":` 这行是什么意思？
   （答案：只有直接运行这个文件时才执行，被 import 时不执行。
   这样别人可以 import 你的函数而不触发副作用）

## 八、整条链路的串联说明

> 我做的项目叫招聘与公司情报分析系统。
> 起因是我想知道数据类岗位到底集中在哪些行业、哪些城市，
> 以及什么样的公司值得去，所以决定自己采集真实数据来回答这个问题。
>
> 数据来源是公开的财经数据接口，能拿到 5500 多家 A 股上市公司的
> 行情、估值、行业分类和财务指标。
>
> 工程上我做了分层：`config` 管配置，`http` 统一处理网络请求的重试和限速，
> `sources` 是数据源适配器，`storage` 负责数据落地。
> 数据分三层存：raw 层保留原始响应，processed 层是清洗后的规范表，
> 最后进 SQLite 供 SQL 分析。
>
> 我特意把"取数"和"解析"拆开，因为解析逻辑经常改，
> 拆开之后可以直接用本地原始数据重跑，不必反复请求接口。
>
> 后面我还会用 scikit-learn 做行业景气度分类，
> 用 FastAPI 提供接口、Streamlit 做看板。

**这段话里已经包含了**：动机、数据来源、架构、工程考虑、技术栈。
这段描述覆盖了动机、数据来源、架构设计、工程考虑与技术栈。
