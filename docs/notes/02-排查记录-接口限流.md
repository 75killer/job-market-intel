# 排查记录：东方财富行情接口被限流事件

> **本文档记录一次完整的外部依赖故障排查过程。**
> 保留全部试错细节，因为排查思路本身比结论更有参考价值——
> 尤其是「连续三次误判」的部分。

---

## 一、事件经过

| 时间 | 事件 |
|---|---|
| T0 | 写采集脚本，跑 1 页 → **成功**，拿到 100 条数据 |
| T1 | 立刻跑全量采集 → **第 1 页就失败**，重试 3 次全败：`ConnectionError: RemoteDisconnected` |
| T2 | 怀疑缺 `Referer`，补上 → **仍然失败** |
| T3 | 做 6 组请求头对照实验 → **全部失败**（含完全不带 header 的默认请求） |
| T4 | 用 PowerShell 测同一接口 → **成功**（拿到 5562 条，甚至能取 K 线） |
| T5 | 结论修正为"Python 的 TLS 被对方拒绝" |
| T6 | 分层诊断：DNS ✅ TCP ✅ TLS1.2/1.3 ✅ 原生 ssl 请求 ✅ urllib ✅ **仅 requests ❌** |
| T7 | 用 `http.client` 逐个复刻 requests 的请求特征 → **全部成功**（说明请求头不是原因） |
| T8 | 发现 `requests` + `Connection: close` 成功一次 → 以为是解法 |
| T9 | 用 8 页 × 2 组做对照验证 → **两组全部失败**（结论再次被推翻） |
| T10 | urllib vs requests 各 10 页对照 → **两组全部 0/10 失败** |
| T11 | 参数矩阵实验（5 种参数组合）→ **全部失败**（排除参数原因） |
| T12 | 回头再测 PowerShell → **也失败了** |
| T13 | **Node.js 测试 → 也失败** |
| T14 | **真相**：不是 Python 的问题，是**对方按 IP 限流**——请求量积累到阈值后，无论用什么客户端、什么参数、什么请求头，全部被拒 |

---

## 二、根因

**东方财富行情接口（`push2.eastmoney.com`）对请求源做了 IP 级限流。**
触发后表现为 `RemoteDisconnected`——TCP 能连、TLS 能握手，但服务端收到请求后
直接断开，连 HTTP 状态码都不返回。

这个行为最容易误导人的地方在于：
- 它**看起来像"客户端兼容性问题"**（因为最初几次请求是成功的）
- 它**看起来像"缺少某个请求头"**（因为失败发生在请求阶段）
- 它**会间歇性恢复**（过一段时间又能成功几次），让你误以为"改对了"

---

## 三、我犯的三个错误（这部分才是重点）

### 错误 1：把"单次成功"当成"问题已修复"

三次犯同一个错误：
```
改了 Referer → 跑一次成功 → 宣布修复
改了 Connection 头 → 跑一次成功 → 宣布修复
改了 HTTP 库 → 跑一次成功 → 宣布修复
```

**为什么这是错的？**
因为被限流的接口本身就会"间歇性放行"。任何改动之后紧接着的一次成功，
都极可能只是**碰上了放行窗口**，跟你的改动毫无关系。

**正确做法**：至少跑 **N 次连续请求**（我后来用 8–10 次），
并且**同时跑一个对照组**（不改任何东西的那组）。如果两组成功率差不多，
说明你的改动没有起作用。

> **结论**：
> "我踩的最大的坑不是技术问题，是**验证方法**的问题——
> 我用单次结果去验证假设，导致连续三次得出了错误的根因。
> 后来我改成'对照组 + 足量样本'的验证方式，才定位到真正的原因是 IP 限流。"

### 错误 2：先改代码，后做诊断

发现失败后，我的第一反应是"改点什么试试"（加个 header、改个参数），
而不是"先确认哪一层坏了"。
结果前 40 分钟全部浪费在错误的假设上。

**正确做法（后来才做的）**：分层排除。
```
DNS 能解析吗？        → 能
TCP 443 能连吗？      → 能
TLS 握手能完成吗？    → 能（1.2 和 1.3 都行）
绕过 requests 直接发原生 HTTP → 能拿到 200
换一个 HTTP 库        → 也能
那问题在哪一层？      → 不在客户端这一侧
```
一旦确认"客户端所有实现都失败"，排查方向立刻从"改代码"转向"看服务端行为"。

### 错误 3：只测一个变量，却没测"时间"这个变量

我从头到尾都假设"服务端行为是恒定的"，所以一直在找"客户端和它的差异"。
但真实情况是**服务端状态随时间变化**（限流计数器累积/衰减）。
我没有在一开始就建立"同一时刻、双组对照"的实验设计，
所以永远分不清"是改动生效了"还是"刚好赶上放行"。

## 四、最终解决方案（工程应对）

既然根因不在我们这一侧，就要用工程手段让系统**在这种环境下依然能工作**：

| 措施 | 实现位置 | 作用 |
|---|---|---|
| **原始数据本地缓存** | `jmintel/cache.py` | 采集一次后反复使用，不再重复请求 |
| **失败先落盘再抛错** | `sources/eastmoney_finance.py` | 采集途中被打断也不丢已拿到的数据 |
| **单源失败不阻塞整体** | `scripts/02_collect_finance.py` | 一个报告期失败，其他报告期继续 |
| **主源降级到备用源** | 项目决策 | 行情接口不可用时，改用财务接口（不同域名，未受限流） |
| **数据源健康巡检** | `scripts/00_health_check.py` | 提前知道哪些源活着，不盲目写代码 |
| **请求限速 + 指数退避** | `jmintel/http.py` | 降低触发限流的概率 |

**这套组合的实际效果**：

> "被限流之后，我没有硬刚（比如换代理、绕风控——那既不道德也不可持续），
> 而是做了三件事：第一，把原始数据落盘，让历史数据变成可复用资产；
> 第二，加了缓存层，重复运行不打接口；第三，把主数据源换成未被限制的
> 财务接口。同时我加了数据源健康巡检脚本，以后写代码之前先确认源是活的。
> 我认为这比'想办法突破对方限制'是更专业的处理方式。"

## 五、可复用的经验总结

1. **"能用一次"≠"能用"。** 任何涉及外部服务的结论，都要用连续多次 + 对照组验证。
2. **排查从分层开始，不要从改代码开始。** DNS → TCP → TLS → 应用层，逐层确认。
3. **区分"客户端差异"和"服务端状态"。** 如果所有客户端实现都失败，问题在服务端。
4. **`RemoteDisconnected` 不一定是网络故障。** 它也可能是服务端主动拒绝（限流/风控）。
5. **原始数据必须落盘。** 它是你对抗"外部依赖不稳定"的唯一底牌。
6. **不要为了拿数据去绕过风控。** 换公开接口、换数据源、用缓存——都是更专业的选择。

## 六、事件总结（60 秒版本）

> "我采集上市公司数据时遇到一个很有意思的问题：脚本第一次跑成功了，
> 第二次就全部失败，报连接被重置。
>
> 我一开始以为是请求头的问题，改了三次，每次改完跑一次都成功，
> 我就以为修好了——结果一跑全量又失败。
>
> 后来我意识到我的验证方法有问题：我拿单次成功当证据，
> 但那个接口本身是间歇性放行的。
>
> 于是我换了方法：先分层排除，从 DNS、TCP、TLS 一路测到应用层，
> 发现换任何 HTTP 库都失败；然后用一个从没改过代码的对照脚本同时测，
> 结果对照组也失败——这就说明问题不在我的代码，而在服务端按 IP 限流。
>
> 确认根因之后我没有去绕限流，而是改了架构：原始数据落盘做缓存、
> 失败时先保存已采集的数据、把主数据源降级到另一个未被限制的接口，
> 还写了一个数据源健康巡检脚本。
>
> 这件事教给我的是：**排查问题时，验证方法比技术知识更容易出错。**"
